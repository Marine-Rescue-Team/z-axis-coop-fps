1세 가지 약속

이것만 지키면 됩니다

아래 내용은 전부 이 세 가지를 지키기 위한 절차입니다.

1
티켓 없이는 작업하지 않는다일을 시작하기 전에 티켓부터 만듭니다. 다른 사람과 다른 사람의 AI가 내가 무엇을 하는지 여기서 읽습니다.
2
폴더마다 담당이 있다자기 담당 폴더는 승인 없이 고칩니다. 남의 폴더를 고치면 그 폴더 담당의 승인이 있어야 합쳐집니다.
3
dev에서 확인한 뒤에 완료한다합쳤다고 끝이 아닙니다. dev에서 문제없이 도는 걸 확인하고 티켓을 닫습니다.

2폴더와 담당

누가 어디를 고치고, 누가 승인하나

리포지토리는 세 폴더로 나뉘고 폴더마다 담당이 있습니다. 규칙은 두 줄입니다.

  • 내 담당 폴더를 고친 PR: 승인 없이 내가 바로 합칩니다.
  • 남의 폴더를 고친 PR: 그 폴더 담당이 승인해야 합쳐집니다.
Client/클라 1, 클라 2 
Server/서버 
Planning/기획 

눌러 보세요: 이 PR은 승인이 필요한가

담당은 리포지토리의 CODEOWNERS 파일에 적혀 있고, 남의 폴더를 고친 PR에는 GitHub이 그 폴더 담당에게 자동으로 승인을 요청합니다. 다른 폴더를 고쳐야 할 일이 생기면 그 폴더 담당에게 티켓으로 요청하는 것이 기본입니다.

다른 담당에게 요청하기

남의 폴더에서 필요한 일이 생기면 직접 고치지 않고 요청 티켓을 만듭니다. 티켓을 만들기만 해서는 상대에게 알림이 가지 않습니다. 아래 두 가지를 해야 알림이 갑니다.

  1. 요청받는 사람을 티켓의 담당자로 지정한다
  2. 본문에서 @아이디로 그 사람을 부른다
gh issue create --title "입장 응답에 번호 추가" \ --assignee server-id \ --body "@server-id 요청: 방 입장 응답에 플레이어 번호를 넣어 주세요완료 조건: 클라이언트가 자기 번호를 받는다폴더: Server/관련 티켓: #12"

server-id 자리에는 상대의 GitHub 아이디를 넣습니다. 알림은 GitHub 알림함, GitHub 모바일 앱, 이메일 중 각자 설정한 곳으로 옵니다. 휴대폰으로 받으려면 GitHub 모바일 앱을 설치합니다.

3브랜치

main, dev, 작업 브랜치

브랜치는 세 종류뿐입니다. 그림은 왼쪽에서 오른쪽으로 시간이 흐릅니다.

  1. 1dev에서 갈라져 나온다. 티켓 하나에 작업 브랜치 하나를 만듭니다.
  2. 2작업 브랜치에서 커밋한다. 여기서는 마음껏 고쳐도 다른 사람에게 영향이 없습니다.
  3. 3PR로 dev에 합친다. 남의 폴더를 고쳤다면 그 담당의 승인이 먼저 필요합니다. 다른 티켓도 같은 방식으로 dev에 모입니다.
  4. 4마일스톤이 끝나면 dev를 main에 합친다. 그 지점에 태그를 붙입니다.
main마일스톤을 통과한 버전만 있습니다. 직접 커밋하지 않습니다.
dev모든 작업이 모이는 곳이고 기본 브랜치(PR을 올릴 때 기본으로 선택되는 브랜치)입니다. 여기에도 직접 커밋하지 않고 PR로만 합칩니다.
feature/번호-설명작업 브랜치. 티켓 번호를 이름에 넣습니다. 예: feature/12-player-move

4티켓의 한 살이

만들기부터 완료까지 일곱 단계

"플레이어 이동"이라는 작업을 예로 따라가 봅니다. 아래로 내리면 위의 보드에서 티켓이 칸을 옮겨 갑니다.

보드는 GitHub의 Projects 화면에 있고 네 칸으로 되어 있습니다. 새 티켓은 "할 일" 칸에 자동으로 들어옵니다. 칸을 옮길 때 사람은 보드에서 카드를 끌어 옮기고, AI는 gh로 옮깁니다. gh는 터미널에서 GitHub을 다루는 공식 도구이고, 단계마다 있는 왼쪽에 초록 줄이 그어진 어두운 상자는 AI가 실행하는 명령의 예시입니다.

할 일
진행 중
dev 확인 중
완료
티켓아직 없음

  1. 1

    먼저 읽는다AI가

    같은 일을 하는 티켓이 이미 있는지, 관련된 작업이 어디까지 됐는지 확인합니다. 다른 사람의 티켓과 PR이 내 작업의 참고 자료입니다.

    gh issue list --state all --search "플레이어 이동"
  2. 2

    티켓을 만든다AI가

    무엇을 할지 적고 마일스톤을 붙입니다. 작업 티켓은 미리 만들어 두지 않고 작업자가 직접 만듭니다. 만들면 GitHub이 번호를 붙여 줍니다. 이 예시에서는 12번, 줄여서 #12입니다.

    gh issue create --title "플레이어 이동" \ --milestone "M1. 혼자 한 판" \ --body "만들 것: 걷기와 시점 회전완료 조건: 빈 맵에서 걷고 둘러볼 수 있다폴더: Client/관련 티켓: 없음"
    티켓 본문에 적는 네 가지
    • 만들 것
    • 완료 조건: 무엇이 되면 끝인지
    • 고치는 폴더
    • 관련 티켓 번호
  3. 3

    시작한다AI가

    티켓을 "진행 중"으로 옮기고, 최신 dev에서 작업 브랜치를 만듭니다. 브랜치 이름에 티켓 번호를 넣습니다.

    git fetch origingit switch -c feature/12-player-move origin/dev
  4. 4

    커밋하고 올린다AI가

    커밋 메시지 앞에 티켓 번호를 [#12]처럼 적고, GitHub에 올립니다. 올라간 커밋은 번호 덕분에 티켓 화면에 자동으로 연결됩니다.

    git add Client/git commit -m "[#12] 플레이어 이동 추가"git push -u origin feature/12-player-move
  5. 5

    PR을 올린다AI가

    dev를 대상으로 PR을 올립니다. 설명에는 Refs #12라고 적어 티켓과 연결합니다.

    이 예시는 클라 담당이 Client/만 고쳤으므로 승인이 필요 없습니다. 남의 폴더를 함께 고쳤다면 여기서 그 폴더 담당의 승인을 기다립니다.

    gh pr create --base dev \ --title "[#12] 플레이어 이동" \ --body "Refs #12"

    Closes #12는 쓰지 않습니다. 합쳐지는 순간 티켓이 닫혀서, dev에서 확인하기도 전에 완료가 되기 때문입니다.

  6. 6

    dev에 합치고 확인한다올린 사람이

    PR을 올린 사람이 dev에 합칩니다. 승인이 필요한 PR이었다면 승인이 난 뒤에 합칩니다. 티켓을 "dev 확인 중"으로 옮기고, dev에서 직접 실행해 완료 조건이 되는지와 다른 기능이 깨지지 않았는지 봅니다.

    문제가 있으면 티켓을 닫지 않고 "진행 중"으로 되돌려 고칩니다.

  7. 7

    티켓을 닫는다AI가

    확인이 끝나면 티켓을 닫습니다. 닫힌 티켓은 보드에서 자동으로 "완료"가 되고, 마일스톤의 진행률이 올라갑니다.

    gh issue close 12 --comment "dev에서 확인 완료"

5마일스톤 끝내기

dev를 main에 합치는 날

마일스톤마다 "[M0] 마일스톤 종료" 같은 종료 티켓이 하나씩 있습니다. 이 티켓만은 사람이 만들지 않고 자동으로 만들어집니다. 마일스톤의 통과 기준을 모두 넘기면 이 순서로 끝냅니다.

  1. 1
    통과 기준을 확인한다GitHub 마일스톤 화면의 통과 기준을 dev에서 하나씩 확인합니다.
  2. 2
    남은 티켓을 정리한다이 마일스톤의 티켓이 모두 닫혔는지 봅니다. 못 끝낸 티켓은 다음 마일스톤으로 옮깁니다.
  3. 3
    dev를 main에 합친다dev에서 main으로 PR을 올립니다. 세 폴더의 변경이 모두 들어 있으므로 각 폴더 담당이 승인한 뒤 합칩니다.
  4. 4
    태그를 붙인다main의 그 지점에 m0, m1처럼 태그를 붙입니다.
  5. 5
    종료 티켓과 마일스톤을 닫는다이것으로 한 단계가 끝납니다.

마일스톤은 어디서 보고 어디서 고치나

  • 보는 곳: 리포지토리의 Issues → Milestones. 마감일, 통과 기준, 진행률이 나옵니다.
  • 고치는 곳: Planning/milestones.yml 하나뿐입니다. 합쳐지면 GitHub 마일스톤에 자동으로 반영됩니다.
  • GitHub 화면에서 직접 고친 내용은 다음 반영 때 덮어써집니다.

규칙 문서에 들어가는 것

  • 작업 전에 읽을 것: 관련 티켓, Planning/의 기획 문서
  • 티켓 없이 작업하거나 커밋하지 않는다
  • 브랜치 이름, 커밋 메시지, PR 작성 규칙
  • 폴더 담당: 자기 폴더는 승인 없이 고치고, 그 밖은 담당에게 티켓으로 요청한다
  • 요청 티켓에는 담당자를 지정하고 @아이디로 부른다
  • 외부 에셋 규칙 (7번 구역의 외부 에셋 항목)

규칙을 바꾸고 싶으면 AGENTS.md를 고치는 PR을 올립니다. 각자 AI에게 따로 지시해서 규칙을 바꾸지 않습니다.

7자주 하는 실수와 요약

자주 하는 실수

실수PR에 Closes #12라고 쓴다

대신Refs #12라고 씁니다. Closes는 합쳐지는 순간 티켓을 닫아 버려서, dev에서 확인하기 전에 완료가 됩니다.

실수급해서 티켓 없이 먼저 고친다

대신한 줄짜리라도 티켓부터 만듭니다. 티켓이 없으면 다른 사람의 AI는 그 변경의 이유를 알 수 없습니다.

실수내 작업에 필요해서 다른 폴더를 같이 고친다

대신그 폴더 담당을 지정한 티켓으로 요청합니다. 꼭 같이 고쳐야 하면 PR에서 그 담당의 승인을 받습니다.

실수출처를 모르는 외부 에셋을 커밋한다

대신공개 리포지토리이므로 출처와 라이선스를 확인해 에셋 목록(Planning/asset-sources.md)에 기록한 에셋만 올립니다. 재배포를 금지하는 라이선스의 에셋은 무료든 유료든 올리지 않습니다.

실수dev나 main에 직접 커밋한다

대신항상 작업 브랜치에서 커밋하고 PR로 합칩니다.

한 장 요약

  1. 관련 티켓을 읽는다
  2. 티켓을 만들고 마일스톤을 붙인다
  3. "진행 중"으로 옮기고 feature/번호-설명 브랜치를 dev에서 만든다
  4. 커밋 메시지 앞에 [#번호]를 적고 GitHub에 올린다
  5. dev로 PR을 올리고 Refs #번호를 적는다. 남의 폴더를 고쳤으면 그 담당의 승인을 받는다
  6. dev에 합치고 "dev 확인 중"에서 직접 확인한다
  7. 티켓을 닫는다. 마일스톤이 끝나면 dev를 main에 합친다

이 문서는 팀이 합의한 작업 방식을 설명합니다. 방식을 바꾸려면 이 문서와 AGENTS.md를 함께 고치는 PR을 올립니다.
